Alat untuk memprofil, menyesuaikan, dan memeriksa eksperimen

Anggaran penggunaan: 10 minit pada pemproses Heron r2 (NOTA: Ini hanya anggaran. Masa jalan anda mungkin berbeza.)

Untuk mendapatkan keputusan yang baik daripada komputer kuantum, anda memerlukan lebih daripada litar yang direka dengan baik. Keadaan semasa peranti, cara litar anda dijadualkan, hingar yang dialami litar, serta bila dan bagaimana kerja anda dijalankan pada unit pemprosesan kuantum (QPU) semuanya menjejaskan kualiti keputusan anda. Qiskit dan IBM Quantum® Compute Service menawarkan set alat pembangun yang semakin berkembang yang mendedahkan maklumat ini. Anda boleh menggunakan alat ini untuk bertindak berdasarkan maklumat itu sebelum anda memperuntukkan masa QPU kepada eksperimen penuh, dan untuk menyahpepijat eksperimen yang telah selesai.

Tutorial ini menggunakan satu eksperimen hujung-ke-hujung untuk menunjukkan cara menggabungkan alat ini pada setiap peringkat aliran kerja pembangunan tipikal. Tidak setiap alat berguna untuk setiap eksperimen, jadi pilih alat yang menjawab soalan yang anda ada tentang beban kerja anda sendiri.

Aliran kerjanya adalah seperti berikut:

  1. Sediakan litar cermin bagi evolusi masa Trotter model Ising medan-melintang linear.

  2. Pilih backend dengan set data penentukuran alternatif yang direka untuk kaedah mitigasi ralat berasaskan model hingar.

  3. Jalankan eksperimen penanda aras peranti supaya transpiler menggunakan sifat peranti terkini apabila ia memilih susun atur.

  4. Periksa maklumat pemasaan bagi litar yang dijadualkan.

  5. Pelajari model hingar Pauli-Lindblad dan bacaan bagi litar.

  6. Jalankan simulasi setempat tanpa hingar, tanpa mitigasi, dan dimitigasi. Simulasi berhingar menggunakan model hingar yang dipelajari untuk menunjukkan berapa banyak peningkatan yang mungkin anda perolehi daripada kaedah mitigasi ralat yang dipilih. Tutorial ini menggunakan pembatalan ralat kebarangkalian (PEC) dan Twirled Readout Error eXtinction (TREX).

  7. Dapatkan anggaran penggunaan tanpa menjalankan pada QPU, untuk menyemak sama ada anda perlu melaraskan eksperimen agar muat dalam bajet anda.

  8. Mulakan session dan cetuskan penentukuran supaya eksperimen menggunakan data penentukuran terkini.

  9. Jalankan eksperimen pada QPU dengan menggunakan Estimator, dan bandingkan keputusan perkakasan dengan pratonton simulasi.

  10. Periksa span pelaksanaan untuk melihat sama ada terdapat jurang ketara antara kumpulan pelaksanaan (ketulan).

Keperluan​

Sebelum memulakan tutorial ini, pastikan anda telah memasang yang berikut:

  • Qiskit SDK v2.3 atau lebih baharu, dengan sokongan visualisasi

  • qiskit-ibm-runtime v0.52.1 or later (pip install qiskit-ibm-runtime)

  • Qiskit Aer (pip install qiskit-aer)

  • Plotly (pip install plotly)

  • Qiskit Device Benchmarking (pip install git+https://github.com/qiskit-community/qiskit-device-benchmarking.git)

Keperluan pelan

Sesetengah langkah dalam tutorial ini tidak tersedia pada setiap pelan:

  • Kerja dry-run (Langkah 2.4 dan 3.5) hanya tersedia pada pelan Flex, Premium, dan On-Prem.

  • Session (Langkah 4.1) tidak tersedia pada Open Plan. Untuk menjalankan dalam batch mode sebaliknya, tetapkan run_calibration = False dalam Langkah 4.1.

Langkah 1: Nyatakan litar dan observable​

Sediakan litar cermin bagi evolusi masa Trotter model Ising medan-melintang linear. Cerminkan litar untuk membatalkan unitari litar dan membentuk litar identiti. Oleh kerana output unggul ialah keadaan semua-sifar, nilai jangkaan unggul bagi setiap observable ZZZ satu-qubit ialah 1. Pencerminan juga menggandakan kedalaman litar, yang menguatkan kesan hingar.

import numpy as np
from qiskit.circuit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp

def construct_ising_circuit(
    num_qubits: int,
    num_trotter_steps: int,
    rx_angle: float,
    barrier: bool = True,
) -> QuantumCircuit:
    circuit = QuantumCircuit(num_qubits)

    for _step in range(num_trotter_steps):
        circuit.rx(rx_angle, range(num_qubits))
        if barrier:
            circuit.barrier()
        for first_qubit in (1, 2):
            for idx in range(first_qubit, num_qubits, 2):
                # equivalent to Rzz(-pi/2):
                circuit.sdg([idx - 1, idx])
                circuit.cz(idx - 1, idx)
        if barrier:
            circuit.barrier()

    return circuit

def mirror_circuit(circuit: QuantumCircuit) -> QuantumCircuit:
    mirror_circ = circuit.copy_empty_like()
    mirror_circ.compose(circuit, inplace=True)
    mirror_circ.barrier()
    mirror_circ.compose(circuit.inverse(), inplace=True)
    mirror_circ.measure_active()
    return mirror_circ
num_qubits = 20
observables = [
    SparsePauliOp("I" * ((num_qubits - 1) - q) + "Z" + "I" * q)
    for q in range(num_qubits)
]

# Free parameters of the demonstration circuit: the number of Trotter steps
# sets the circuit depth, and rx_angle is the transverse-field rotation angle
# applied in each step (pi/4 makes the dynamics non-Clifford)
num_trotter_steps = 5
rx_angle = np.pi / 4

circuit = construct_ising_circuit(
    num_qubits, num_trotter_steps, rx_angle, barrier=False
)
mirrored_circuit = mirror_circuit(circuit)
mirrored_circuit.draw(
    "mpl", fold=-1, scale=0.3, idle_wires=False, measure_arrows=False
)

Langkah 2: Optimumkan untuk pelaksanaan perkakasan kuantum​

2.1 Gunakan penentukuran alternatif jika berkenaan​

IBM® menentukur QPUnya secara berkala untuk prestasi yang baik merentas kes penggunaan umum. Namun, sesetengah beban kerja mendapat manfaat daripada arahan yang parameternya ditala secara berbeza. Untuk maklumat lanjut, rujuk Arahan yang ditentukur khas.

Tutorial ini menggunakan set data penentukuran alternatif yang dipanggil slow_gates_ac. Penentukuran ini mengandungi gate cz yang lebih perlahan dan memodulasikan pincang sistem dua-aras (TLS) untuk menstabilkan ralat peranti dari semasa ke semasa. Perubahan ini memanfaatkan kaedah mitigasi ralat yang bergantung pada model hingar yang dipelajari. Penentukuran slow_gates_ac hanya tersedia pada QPU Heron. Jika anda menjalankan pada QPU Nighthawk, gunakan slow_gates sebaliknya.

from qiskit_ibm_runtime import QiskitRuntimeService

service = QiskitRuntimeService()
# Use slow_gates_ac because this tutorial uses a noise-learning-based mitigation method
backend = service.backend("ibm_kingston", calibration_id="slow_gates_ac")

2.2 Jalankan penanda aras peranti masa nyata​

Salah satu peringkat transpilasi yang paling kritikal ialah pemilihan susun atur, yang memetakan qubit maya dalam litar kepada qubit fizikal pada peranti sasaran. Susun atur yang baik meminimumkan bilangan operasi SWAP yang diperlukan dan meletakkan litar pada qubit berprestasi terbaik, jadi kualiti susun atur awal boleh menjejaskan kualiti keputusan anda dengan ketara.

Rutin penanda aras berkala dijalankan pada setiap QPU IBM untuk melaporkan prestasi semasa qubitnya: masa relaksasi (T1T_1T1​), masa koheren (T2T_2T2​), ralat bacaan, dan ralat gate satu- dan dua-qubit. Transpiler Qiskit menggunakan metrik ini semasa pemilihan susun atur.

Namun, sifat qubit superkonduktor boleh hanyut pada skala masa yang lebih singkat, dan kecacatan sementara, yang dikenali sebagai TLS, boleh menjejaskan buat sementara qubit yang berprestasi baik semasa penentukuran. Jika transpiler menggunakan maklumat yang usang, ia tidak dapat memilih susun atur terbaik. Oleh itu, mungkin berbaloi untuk meluangkan sedikit masa QPU untuk mencirikan peranti sebelum anda memilih susun atur.

Rujuk tutorial Segarkan sifat backend dengan penanda aras masa nyata untuk panduan terperinci. Suite pencirian membina beberapa eksperimen, menghantar berbilang kerja, dan memadankan keputusan. Proses ini boleh mengambil masa beberapa minit secara keseluruhan. Dayakan pengelogan peringkat INFO supaya setiap peringkat mencetak kemajuannya semasa ia berjalan.

import sys
import logging

logger = logging.getLogger("qiskit_device_benchmarking")
logger.setLevel(logging.INFO)
logger.addHandler(logging.StreamHandler(stream=sys.stdout))

2.4 Visualisasikan pemasaan litar​

Selain arahan dalam litar, anda mungkin ingin memvisualisasikan jadual litar, untuk mencari masa melahu pada qubit atau penjajaran arahan yang tidak cekap. Anda boleh mendapatkan maklumat pemasaan yang paling terperinci dan tepat daripada IBM Quantum Compute Service dengan menggunakan mod dry-run.

Litar dalam tutorial ini bersifat statik, jadi jadualnya tidak begitu bermaklumat. Anda boleh mendapatkan maklumat pemasaan yang serupa secara setempat daripada litar dan sifat Backend, contohnya dengan menggunakan timeline drawer yang terbina dalam Qiskit. Tutorial ini menyertakan langkah ini untuk menunjukkan cara meminta dan memvisualisasikan maklumat pemasaan. Maklumat pemasaan daripada perkhidmatan paling berguna untuk litar dinamik. Litar dinamik mengandungi pengukuran pertengahan litar, operasi bersyarat, dan feedforward, yang menambah operasi tersirat seperti menyiarkan keputusan pengukuran dan menentukan cabang. Pemasaan operasi ini tidak dapat ditentukan daripada litar dan sifat Backend sahaja.

Rujuk Visualize circuit timing untuk maklumat lanjut. Pemasaan litar berjadual hanya tersedia untuk job Sampler dan Executor, jadi sel berikut menghantar litar dalam mod dry-run dengan menggunakan Sampler. Job yang anda hantar dalam mod dry-run tidak dijalankan pada QPU sebenar dan tidak dikenakan caj.

Langkah 3: Gunakan pengurangan ralat dan uji secara setempat​

3.1 Cliffordkan litar​

Kos simulasi hingar am meningkat secara eksponen dengan bilangan qubit, dan kebanyakan komputer riba tidak dapat mensimulasikan lebih daripada kira-kira 32 qubit. Oleh itu, mula-mula tukarkan litar kepada litar Clifford, yang dapat dikendalikan jauh lebih cekap oleh simulator penstabil. Penukaran ini membundarkan setiap sudut putaran kepada sudut Clifford, jadi litar yang disimulasikan menghampiri litar asal dan bukan menghasilkannya semula.

from qiskit.transpiler import PassManager
from qiskit_ibm_runtime.transpiler.passes import ConvertISAToClifford

clifford_circuit = PassManager([ConvertISAToClifford()]).run(isa_circuit)
clifford_pubs = [(clifford_circuit, isa_observables)]

3.2 Gunakan PEC dengan TREX​

Memilih kaedah pengurangan ralat yang mengimbangi kos dan ketepatan untuk eksperimen khusus anda boleh menjadi sukar. Anda boleh menggunakan kemahiran ejen AI select-error-mitigation untuk menganalisis kaedah yang tersedia bagi beban kerja anda. Kemahiran ini memaparkan laporan ringkasan yang menerangkan sama ada setiap kaedah dipilih dan sebabnya.

Rujuk repositori GitHub Qiskit AI skills untuk maklumat lanjut. Tutorial ini menggunakan PEC dengan TREX secara langsung, supaya anda dapat melengkapkannya tanpa ejen AI.

PEC ialah teknik yang mengurangkan hingar kuantum apabila anda mengira nilai jangkaan bagi observable. Dalam keadaan ideal, PEC boleh menghasilkan anggaran tanpa bias bagi nilai jangkaan. Ia mempelajari hingar bagi setiap lapisan get dua qubit, kemudian menjalankan satu ensemble litar yang, secara purata, menggunakan songsangan hingar tersebut. PEC menggunakan Pauli twirling untuk menyesuaikan hingar menjadi saluran Pauli, yang boleh dipelajari dan disongsangkan dengan cekap.

Dalam praktiknya, PEC hanya setepat model hingar yang dipelajari. Model sparse Pauli-Lindblad hanya merangkumi sebutan ralat satu dan dua qubit pada qubit berjiran, dan ia tidak dapat menangkap sepenuhnya kesan seperti crosstalk antara qubit yang jauh atau ralat yang berkorelasi masa. Hingar peranti juga boleh hanyut antara pembelajaran hingar dan pelaksanaan. PEC tidak membatalkan hingar yang terlepas daripada model, dan ia terlebih mengimbangi hingar yang dianggar berlebihan oleh model. Oleh itu, keputusan yang telah dikurangkan ralatnya masih boleh menyimpang daripada nilai ideal ke mana-mana arah.

TREX ialah teknik yang mengurangkan ralat pengukuran, dan berguna apabila anda menganggar nilai jangkaan bagi observable Pauli. Ia bergantung pada measurement twirling, yang mendiagonalkan matriks pindahan ralat bacaan dan memudahkan penyongsangannya. TREX mempelajari sebutan penskalaan semula daripada saluran hingar pepenjuru dengan mengukur litar penentukuran twirled yang dimulakan dalam keadaan sifar. Anda boleh mengaktifkan kedua-dua PEC dan TREX dengan menetapkan pilihan Estimator. Tutorial ini menggunakan pelaksanaan sisi klien bagi antara muka SamplerV2 dan EstimatorV2 Qiskit, yang diperkenalkan dalam qiskit-ibm-runtime v0.50.0. Primitif sisi klien ini melakukan kebanyakan pra-pemprosesan dan pasca-pemprosesan secara setempat dan menyerahkan pelaksanaan kepada primitif Executor. Apabila primitif berjalan di sisi klien, anda mendapat ketelusan yang lebih tinggi, maklum balas yang lebih pantas semasa penyahpepijatan, dan kawalan yang lebih halus.

Primitif sisi klien melaksanakan API yang sama seperti primitif sisi pelayan lama. Oleh itu, anda biasanya boleh beralih kepada primitif sisi klien dengan menukar penyata import sahaja. Aktifkan pengelogan peringkat INFO untuk melihat kemajuan pra-pemprosesan dan pasca-pemprosesan sisi klien.

import logging

logger = logging.getLogger("qiskit_ibm_runtime")
logger.setLevel(logging.INFO)
from qiskit_ibm_runtime.executor_estimator import Estimator

estimator = Estimator(mode=backend)
# Enable TREX
estimator.options.resilience.measure_mitigation = True
# Enable PEC
estimator.options.resilience.pec_mitigation = True

3.3 Pelajari model hingar dan jalankan litar yang telah dicliffordkan​

Kedua-dua PEC dan TREX memerlukan pembelajaran hingar, yang boleh anda lakukan dengan NoiseLearnerV3. Langkah-langkahnya adalah seperti berikut:

  1. Cari lapisan get dua qubit dan lapisan pengukuran yang unik dalam litar, masing-masing untuk protokol Pauli-Lindblad dan TREX.

  2. Hantar lapisan tersebut kepada NoiseLearnerV3 untuk mempelajari model hingar.

  3. Tukarkan model hingar yang dipelajari kepada peta Pauli-Lindblad.

Estimator tidak menggunakan model hingar TREX yang dipelajari terlebih dahulu. Sebaliknya, ia melakukan pembelajaran TREX sendiri. Kod berikut tetap mempelajari kedua-dua model, kerana simulasi berhingar menggunakan model bacaan yang dipelajari.

Rujuk Noise learning helper untuk maklumat lanjut tentang NoiseLearnerV3. Selain eksperimen pembelajaran hingar, jalankan litar yang telah dicliffordkan pada QPU. Langkah ini tidak sentiasa diperlukan, tetapi ia menyediakan perbandingan untuk keputusan simulasi dalam Langkah 3.4.4. Jalankan kedua-duanya dalam satu batch untuk meminimumkan hanyutan profil hingar antara keduanya.

pubs = [(isa_circuit, isa_observables)]
# Specify types="all" to find layers for both Pauli-Lindblad and TREX learning
layers = estimator.find_unique_layers(pubs, types="all")
print(f"Number of unique layers found: {len(layers)}")

from qiskit_ibm_runtime import NoiseLearnerV3

with Batch(backend) as batch:
    learner = NoiseLearnerV3(batch)
    learner.options.num_randomizations = 64
    learner.options.shots_per_randomization = 128
    learner.options.environment.job_tags = [
        "noise-learning",
        f"{len(layers)} layers",
    ]

4.1 Mulakan Session dan jalankan penentukuran​

Penentukuran QPU mengoptimumkan banyak parameter yang mentakrifkan isyarat elektrik yang memacu get dan operasi kuantum. Untuk meningkatkan lagi keputusan, anda boleh mencuba perkara berikut:

  • Tingkatkan bilangan shot atau rawak untuk mengurangkan ketidakpastian statistik bagi anggaran yang dikurangkan ralatnya. Kos meningkat mengikut overhead pensampelan PEC.

  • Pelajari semula model hingar sejurus sebelum eksperimen, dalam Session yang sama, untuk mengurangkan kesan hanyutan hingar.

  • Pelajari model hingar dengan lebih tepat dengan meningkatkan pilihan num_randomizations, shots_per_randomization, atau layer_pair_depths bagi NoiseLearnerV3. Ralat dalam kadar yang dipelajari membiaskan keputusan yang dikurangkan ralatnya, dan shot PEC tambahan tidak menghapuskan bias ini.

  • Tambahkan non-Markovian error checks untuk mengesan shot yang berkemungkinan rosak akibat ralat bukan Markov, yang tidak diterangkan oleh model hingar yang dipelajari. Kemudian buang shot tersebut melalui pascapemilihan. Gunakan semakan yang sama apabila anda mempelajari model hingar, dengan menggunakan pilihan bit_flip_checks bagi NoiseLearnerV3. Jika tidak, model yang dipelajari merangkumi ralat yang dihapuskan oleh pascapemilihan daripada eksperimen, dan PEC terlebih mengimbanginya. Pascapemilihan yang lebih ketat membuang lebih banyak shot, jadi imbangkan peningkatan ketepatan dengan bilangan shot yang anda kekalkan.

4.4 Periksa execution span​

Apabila anda menghantar litar dengan pelbagai konfigurasi, seperti dengan gate twirling, IBM Quantum Compute Service tidak semestinya menjalankan semua konfigurasi litar pada masa yang sama. Sebaliknya, ia mengumpulkannya kepada ketulan dan menjalankan satu ketulan bagi setiap gelung shot. Gelung shot ialah satu pusingan pelaksanaan pada perkakasan kuantum, yang mana setiap litar dalam ketulan dijalankan untuk bilangan shot yang diminta.

Semua job yang dihantar kepada QPU sebenar memerlukan sedikit pra-pemprosesan klasik, seperti penterjemahan kepada denyut yang boleh dihantar ke perkakasan. Oleh kerana pra-pemprosesan ini boleh dilakukan secara selari, perkhidmatan mengeluarkan daripada baris gilir dan memulakan beberapa job sekali gus. Walau bagaimanapun, QPU hanya dapat memproses satu unit kerja pada satu masa. Oleh itu, jika job anda menjana beberapa ketulan, ketulan itu mungkin diselang-seli dengan ketulan job pengguna lain, dan setiap ketulan mungkin perlu menunggu gilirannya pada QPU.

Metadata keputusan job melaporkan pemasaan pelaksanaan QPU bagi setiap ketulan. Visualisasi berikut menunjukkan sama ada terdapat jurang yang ketara antara pelaksanaan ketulan dalam job anda. Jika jurang itu lebih lebar daripada yang boleh diterima oleh eksperimen anda, anda mungkin mahu menjalankan semula job, atau menggunakan mod pelaksanaan session, yang memberi beban kerja anda akses eksklusif kepada QPU.

Langkah seterusnya​

Cadangan
  • Jalankan semula eksperimen dengan dan tanpa penentukuran slow_gates_ac (Langkah 2.1), sifat peranti yang disegarkan (Langkah 2.2), atau penentukuran Session (Langkah 4.1) untuk mengukur sejauh mana setiap alat meningkatkan keputusan bagi beban kerja anda.
  • Cuba kaedah pengurangan ralat yang lebih murah seperti zero-noise extrapolation (ZNE), dan gunakan simulasi setempat serta anggaran penggunaan dry-run untuk membandingkan kos dan ketepatannya dengan PEC. Kemahiran ejen AI select-error-mitigation boleh membantu anda membuat pilihan ini.
  • Terokai set pencirian penuh, termasuk randomized benchmarking, dalam tutorial Refresh backend properties with real-time benchmarking.
  • Ketahui lebih lanjut tentang primitif sisi klien dan Executor dalam Migrate from server-side to client-side Sampler and Estimator.
  • Gunakan alat ini pada eksperimen anda sendiri. Mulakan dengan alat yang menangani sumber ketidakpastian terbesar anda, seperti kualiti peranti, hingar, kos, atau pemasaan pelaksanaan.
